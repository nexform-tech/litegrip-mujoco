# LiteGrip MuJoCo 样例

五个层层递进的例程：读模型 → 在仿真里让它动 → 手把手教它一段动作、再放给两边 →
最后把两边对接起来。「跑哪个、怎么跑」看这里；「上真机之前必须确认什么」也看这里。

[English](README.md) · **简体中文**

| 文件 | 方向 | 要真机吗 |
| --- | --- | --- |
| [`01_hello_sim.py`](01_hello_sim.py) | 只读状态，不运动 | **不要** |
| [`02_move_sim.py`](02_move_sim.py) | 只在仿真里运动 | **不要** |
| [`03_trajectory.py`](03_trajectory.py) | 在真机上录，回放给两边 | 要（`--dry-run` 跑整条链路，`--play` 只读文件） |
| [`04_mirror_real.py`](04_mirror_real.py) | 真机 → 仿真 | 要（`--dry-run` 用替身顶替） |
| [`05_dual_control.py`](05_dual_control.py) | 仿真 → 真机 | 要（`--dry-run` 用替身顶替） |

## 运行前准备

```bash
cd /path/to/litegrip-mujoco
python3 -m pip install -e ".[dev]"                    # 01–02
python3 -m pip install -e /path/to/litegrip-python     # 03–05
```

在仓库根目录下跑：本包是 src 布局，没做 editable 安装就 `import litegrip_mujoco`
不到。例程自己会把 `src/` 塞进 `sys.path`，也会在解释器缺 `mujoco` 而仓库里有
`./.venv` 时重跑到那个解释器里，但这两条都不能替代安装。

真机 SDK **没有发布到 PyPI**：`pip install litegrip` 装到的不是它，已发布的版本里也
没有带这套接口的。三个真机样例共用**一份**检出，
[`nexform-tech/litegrip-python`](https://github.com/nexform-tech/litegrip-python)，按
下面的顺序找：

1. `$LITEGRIP_SDK_DIR`，指向**包含** `litegrip` 包的那个目录——src 布局下是
   `<仓库>/src`，不是包目录、也不是仓库根。
2. 本仓库旁边的同级检出：`../litegrip-python`，先按 `src/` 试，再按仓库根试。
3. 当前解释器里装着的 `litegrip`。

**别**把 `LITEGRIP_SDK_DIR` 指到一个没有 `litegrip` 包的目录上：例程会停下来解释，
而不是转去别处 import 一个同名的包。另一个仓库也发了个叫 `litegrip` 的包，
`__version__` 同样是 2.2.0，但没有轨迹接口——版本号分不出来，开跑前的
`check_sdk_api()` 能分出来，它会点名缺哪几个成员（`LiteGrip.record_start`、
`LiteGrip.poll`、`Trajectory.load`……），而不是等到控制循环里才炸。

跑 03、04、05 之前先把 CAN 拉起来：

```bash
sudo ip link set can0 up type can bitrate 1000000
ip -details link show can0
```

> **03、04、05 会真的动电机。** 先读[上真机之前](#上真机之前)。

## 一个开度，几种写法

同一个夹爪有好几种描述方式，混着用是绝大多数困惑的来源：

| 写法 | 范围 | 含义 |
| --- | --- | --- |
| 移动副关节 | `0 … 0.042726` m | **单指**行程；`0` 是张开，所以关节值越大开度越小 |
| **归一化开度** | `0 … 1` | **两边唯一共用的量**；`0` 闭合、`1` 张开（`frac_open()`） |
| 开口行程 | `0 … 85.452` mm | 本仓的毫米口径（`get_position()`） |
| 钳口间隙 | `1.548 … 87` mm | 两个指面的实际距离（`gap_mm()`） |
| 仿真关节角 | `0 … -1.14` rad | MuJoCo 模型里的那个关节（`get_position_rad()`） |
| 真机标定角 | `+1.776 … -0.064` rad | **真机**报的角，来自标定文件 |

最后两行不是同一个刻度，也不是差一个单位换算：仿真关节走 `0 … -1.14 rad`，真机电机走
`+1.776 … -0.064 rad`，同一个数字在两边指的是完全不同的开度。只有归一化开度在两边
含义相同——这就是所有例程都从它换算的原因。

**例程在弧度和归一化开度之间直接换，不经过毫米**：标定文件带着它自己保存时的
`rad_to_mm`。本仓的真实刻度是全行程 85.452 mm，SDK 名义的 `max_stroke_mm` 是
120 mm，而上位机写出来的标定文件两个数都不带。走毫米就等于引入一个文件未必认的刻度。
实现见 `_common.fraction_to_target_rad` 与 `_common.rad_to_fraction`。

## 01 只读状态

只读模型，不运动。不接真机、不碰 CAN、不装 SDK 也能跑——而且整个文件里没有任何一个
运动调用：`sim.pump()` 只推进窗口事件和时钟，你放多久爪子都停在原地。这条不是嘴上
说说，可以自己查：

```bash
grep -n "command_fraction\|command_joint\|set_frac_open\|settle(\|reset(\|goto(\|grasp(\|send_mit_frame" examples/01_hello_sim.py
# （无匹配；出现的 `frac_open()` 只是读）
```

1. **模型常量**——指关节个数、单指行程、自带 MJCF 实际的钳口开口、以及当前生效的力上限。
2. **当前开度（三种写法）**——归一化开度、开口毫米、钳口间隙，并排给出。
3. **实时状态行**——有窗口时一直刷新，按 **Esc** 或 **Q** 退出。

```bash
python3 examples/01_hello_sim.py                # 开窗口，完整演示
python3 examples/01_hello_sim.py --headless     # 无窗口，退出码 0
python3 examples/01_hello_sim.py --scene        # 用带台面/工件的场景，而不是纯夹爪
```

## 02 仿真运动

同一个夹爪，这次驱动它，但仍然只有 MuJoCo：

1. **限速行程**——走满一程约 1.05 s（本机实测，见下）：单指按 42.73 mm/s 走，两指
   对冲，所以**钳口**的变化速度是它的两倍——真机规格的 85 mm/s。
2. **中间位定位**——给一个归一化开度，`settle()` 等到指爪真的到位。

```bash
python3 examples/02_move_sim.py                 # 开窗口，完整演示
python3 examples/02_move_sim.py --headless      # 无窗口，退出码 0
python3 examples/02_move_sim.py --speed 0.02    # 放慢：走满一程约 2 s
python3 examples/02_move_sim.py --force 20      # 夹持力上限 20 N
python3 examples/02_move_sim.py --scene         # 追加一段夹工件（第 3 节）
```

`--speed` 是**单指**速度（m/s），所以默认的 `0.04273` 就是真机规格的 85 mm/s
**钳口**变化速度。实测时间，原样摘自 `python3 examples/02_move_sim.py --headless`：

```text
   → 闭合：用掉 1.050 s 仿真时间 · 到位
   → 张开：用掉 1.057 s 仿真时间 · 到位
   命令  50.0% → 实测  50.0% · 开口 44.26 mm · 0.556 s · 到位
   命令  25.0% → 实测  25.0% · 开口 22.90 mm · 0.300 s · 到位
   命令  75.0% → 实测  75.0% · 开口 65.65 mm · 0.557 s · 到位
```

**别**在这里找 `--object-mm`、`--hold`、`--pull`、`--slip`：本样例没有可抓可拉的东西，
argparse 会直接以退出码 2 拒掉这些参数，而不是忽略它们。那些属于 PyBullet 仓库的
`03_grasp.py`；本仓没有那个样例，`--scene` 的那一节就是全部的抓取演示。

**别**把 `grasp()` 当成「施加这个力」：它的实际行为见
[`grasp()` 到底做了什么](#grasp-到底做了什么)。

## 03 轨迹录制与回放

手把手教夹爪一段动作，存下来，再同时放给**真机**和窗口：

1. **录制。** 电机进零重力——力被关掉，你自己推动手指走完这段动作——同时 SDK 在
   后台按 100 Hz 采样开度。按 **Enter / 空格**结束录制，或给 `--record 6` 让它自己
   停；**Esc / Q** 是「这段不要了」，不存盘。窗口全程跟着你的手走。
2. **存盘。** 录制存到 `~/.litegrip/trajectories/`，文件名带样例名和时间戳，所以第二
   次录制不会覆盖第一次。仓库里不写任何东西：轨迹是在某一台机器上量出来的数据。
3. **确认。** 录完**不会**自己接着回放：按 **Enter / 空格**开始回放，或 **Esc / Q**
   先不放。这几秒就是留给你把手从行程里拿出来的——电机一旦开始动就晚了。
4. **回放。** 同一条轨迹既驱动电机，也把仿真手指直接摆到它的**实测**位置上，所以窗口
   里看到的就是真机正在做的事。轨迹放完手指停在终点，不会自己回到起点。

```bash
python3 examples/03_trajectory.py --calib ~/.litegrip/litegrip_calibration.json
python3 examples/03_trajectory.py --record 6 --calib ~/.litegrip/litegrip_calibration.json
python3 examples/03_trajectory.py --dry-run --calib ~/.litegrip/litegrip_calibration.json
python3 examples/03_trajectory.py --play 03_hand_taught-20260929-120000
python3 examples/03_trajectory.py --play 03_hand_taught-20260929-120000 --real
python3 examples/03_trajectory.py --play 03_hand_taught-20260929-120000 --speed 0.5 --headless
```

`--dry-run` 完全不需要真机：仿真自己当那台夹爪，主循环按一条脚本曲线走开度，后台录制
线程照常按 100 Hz 采样——和接真机时是同一段代码。存盘、读回、回放整条链路都跑到，
少的只有 CAN 报文。

轨迹存的是**归一化开度**，不是角度，所以一台夹爪上教的动作可以在另一台上放，换一台
机器的标定读同一条轨迹，开度含义不变。只给名字时会去 `~/.litegrip/trajectories` 下
找并补 `.lgt`；带 `/` 的路径按原样用。

单给 `--play` 不碰任何真机：不连接、不使能、一帧都不发，只读文件、只灌窗口——这是本
样例唯一一条不需要夹爪就能跑的路。加 `--real` 才会把同一条轨迹也下发给真机。读回来的
记录带着录制时的 `can_id` 和安装方向，本样例把它们打出来然后**不用**：换算走的是
**本机**的标定，因为开度在哪儿都是同一个含义，角度不是。

回放命令的是**位置**，不是力。录到的力矩只作为诊断留在文件里，绝不前馈，所以一段顶着
工件录下来的挤压动作，回放时就成了一条位置曲线，压多大取决于当时的 `kp`——你教的夹持
力不会被保留。要可重复的夹持，回放完再调 SDK 的 `grasp(force_n=...)`。

**这里没有鼠标点击。** PyBullet 那版是点一下窗口才开始回放；MuJoCo 的
`launch_passive` 只给按键回调、不给鼠标事件，所以本样例改成按 **Enter / 空格**。确认
这一步本身——也就是「不让回放顺着你的手直接开始」——没有变。

### 相位之间由本样例自己喂帧

`record_stop()` 把电机交回闭环控制之后就停了：刚才只有 SDK 的录制线程在发帧，回放还
没开始。**使能态**的电机听不到帧就会锁通信丢失故障（0xD）——见
[为什么「只是看」也得持续发帧](#为什么只是看也得持续发帧)。所以本样例在每一个空档里
按 200 Hz 发「**锁在实测位置**」的保持帧：`enable()` 之后、录制与回放之间（这里面还
包含等你确认的那一段，是全程最长的空档）、以及回放结束到你退出之前。它不命令任何
运动，目标**就是**电机报出来的位置，前馈为零。

**别**在录制或回放进行中自己发帧。那两条都是 SDK 的后台线程在占总线，同一根线上再插
一路会把轨迹撕碎。本样例的保持帧因此严格只在相位之间，绝不在相位之内。

`--dry-run` 是例外，它根本不是保持帧：替身没有总线，没有东西要保活，所以它一帧都不发。

## 04 真机控制仿真

真机是事实来源，仿真是显示器。每帧读一次真机位置，用 `set_frac_open()` 把仿真手指直接
摆过去——纯运动学，不走动力学——所以窗口显示的是真机此刻在哪，没有它自己的滞后和漂移。

两种用法：

- **用手推**（`--zero-gravity`，推荐）：电机失力，你可以自己推动手指，窗口跟着你的手走。
  运行中按 **Z** 在失力/使能之间切换。
- **看别的程序驱动它**（`--passive`）：本样例只连接、只读，喂帧留给那个程序——它不使能
  电机，也一帧都不发。

```bash
python3 examples/04_mirror_real.py --zero-gravity --calib ~/.litegrip/litegrip_calibration.json
python3 examples/04_mirror_real.py                  # 镜像（保持帧让它活着）
python3 examples/04_mirror_real.py --passive        # 只读，喂帧交给别人
python3 examples/04_mirror_real.py --headless       # 只在终端里读数
python3 examples/04_mirror_real.py --duration 10    # 10 s 后自动退出
python3 examples/04_mirror_real.py --dry-run --duration 10   # 不碰 CAN，脚本化替身
```

和 05 一样，它每次运行都会读一份标定文件。没给 `--calib` 就用 SDK 包里那份出厂标定
——见[上真机之前](#上真机之前)。

`--dry-run` 换上 `DryRunGripper`，由另一个线程按
`open() → close() → goto(42.7 mm) → grasp(10 N)` 循环驱动它，镜像才有东西可跟。θ →
开度的换算与接真机时是同一条代码路径。它**一帧都不发**——这不是 `--passive` 那种「保持
安静」，而是替身的性质：它没有总线，锁不了 0xD，也没有东西需要喂。Z 键在这条路上因此
被明确拒掉并说明原因，而不是看着能用、按下去没反应。

### 为什么「只是看」也得持续发帧

**使能态**的电机静默约 **0.9 s** 就会锁通信丢失故障（0xD）——红灯闪、位置照样读得出、
指令被静默忽略。这 0.9 s 是 SDK 在这台硬件上实测的；`TIMEOUT` 寄存器（RID 9）和它
对不上（一次读到 8000 ms，另一次读到 0）且被标成「待查」，所以这里按实测走。光看着
窗口不喂帧，就足够把夹爪看哑。

所以默认模式不是只读：它按 200 Hz 发「**锁在实测位置**」的保持帧——目标是手指现在就在
的位置，速度为零、前馈为零。它不命令任何运动，只是给手指一点刚度、并喂住看门狗。想反
过来背驱它，加 `--zero-gravity`（或按 Z），同样发帧但 kp/kd 归零。

**别的程序**正在驱动真机时才用 `--passive`：本样例不发帧、不使能、并禁掉 Z 键，两边
不会抢总线。代价是那个程序得自己喂电机，否则它 0.9 s 后照样锁 0xD。**别**在单跑本样例
时加 `--passive`。

`--zero-gravity`（或 Z）让夹爪变**软**，手指可以被背驱，也可能因自重下垂。使能前先托住。

退出时是**失能**（0xFD），而不是补发一帧重新锁位：单独一帧后面没有下文，使能态的电机
一秒内就会锁 0xD，而那时已经没人清了。所以退出后夹爪是松的，手指可能因自重滑动。

## 05 仿真控制真机

窗口同时是两样东西：**键盘**在下命令，窗口在**显示**真机在哪。使能电机不会让它动——
本样例先读你现在的位置、在窗口里显示出来并锁在那里，你不按键它不动。

| 按键 | 作用 |
| --- | --- |
| **←** / **→** | 目标开度，一下一档 5%（`aperture_down` / `aperture_up`） |
| **↓** / **↑** | 速度上限，一下一档 10% |
| **-** / **=** | 夹持力，一下一档 5 N |
| **空格** | 停：保持当前目标，不再下运动指令 |
| **H** | 回到全开 |
| **Esc** / **Q** | 退出 |

1. 按一下方向键。按键**就是**命令，没有「发送」键。真机按 200 Hz 朝目标走，仿真手指
   镜像的是它的**实测**位置，所以手指是落后于目标、而不是跳到目标。这个差值就是跟踪
   误差；被工件顶住时它一直收不回来——这就是你判断「夹住了」的依据。
2. 随时改**速度**，运动前运动中都可以。它限制的是位置目标每帧能涨多快，按单指额定
   85 mm/s 的百分比算。100% = 「最多 85 mm/s」；超过 100% 按 100% 处理，并且会打印
   出来。
3. 改**力**。它成为随帧下发的前馈力矩，且只在闭合方向生效（张开时施加夹持力会跟电机
   顶着干），并且只在目标到位之后才加。
4. 按 **Esc** 或 **Q** 退出。停发帧、电机**失能**（0xFD）：手指变松、夹着的工件会掉，
   但电机上不会留下锁死的通信故障。

> **没有确认这一步。** 一个按键值**就是**一条命令，所以按一下方向键就是给真机下了一条
> 真命令。手指在行程里的时候别按，按之前先把行程清空。

```bash
python3 examples/05_dual_control.py --calib ~/.litegrip/litegrip_calibration.json
python3 examples/05_dual_control.py --dry-run         # 只开窗口，从不碰 CAN
python3 examples/05_dual_control.py --speed 40        # 速度上限从 40% 起步
python3 examples/05_dual_control.py --force 20 --channel can1
```

两次按键之间，本样例按 200 Hz 持续发当前位置。这不是「保活的小技巧」：使能态的电机
静默约 0.9 s 就锁通信丢失故障（0xD），**停着不动才是出事的那件事**。

**这里是与 PyBullet 版本差别最大的地方。** 那一版在 PyBullet 窗口里放三个滑条；
MuJoCo 查看器没有可以在运行中往仿真里加的控件，所以命令改成离散步进的按键，当前的
目标、速度、力通过窗口状态文字和终端回显。按一下是走一个固定档位，不是连续拖动。这是
能力缺失导致的**有意偏离**，不是缺陷。

`--dry-run` 跑同一个循环，但没有 CAN 报文、也没有实测位置：窗口跟的是**命令值**而不是
真机，状态行上带 `dry-run` 提醒你，替身 `DryRunGripper` 按真机的 θ 刻度回答，所以换算
路径与接真机时一致。

`--headless` 会被拒，除非同时给了 `--dry-run`：键盘就是输入设备，无窗口就没有输入。
在 `--dry-run --headless` 下，「那只手」由一段脚本顶替，按 10.5 s 的周期走四个目标位
——CI 和本文档里的输出就是这么跑出来的。

### 为什么必须是斜坡

MIT 帧的位置项是 `kp × (q_target − q_actual)`，而 `kp` 是标定文件里的一项、不是常量。
SDK 默认的 `kp = 100 Nm/rad` 下，把目标当阶跃下发，一帧就要 `100 × 1.845 rad ≈
185 Nm`，而电机额定只有 10 Nm 上下；本机当前 `kp = 5.0`，同样的阶跃约 9 Nm，在额定之
内。电流一饱和，电机就锁欠压/过流故障，之后位置照报、命令全不理——也就是红灯闪、
「能读不能控」。

斜坡保留下来是因为它不依赖那个数字：它限住的是**位置目标**一帧最多走多远，不管 `kp`
配成多少。每帧都从电机**当前所在**往前走一格，所以单帧的力矩需求远低于额定。SDK 自己
的 `goto_rad` 也是为同样的原因加的斜坡。

这也是为什么速度限制限的是**目标**、不是键盘：按住方向键不放、或者按得再快，电机每帧
也只走一格——按键重复的速度根本到不了总线上。启动时本样例会把这一格打出来：

```text
   位置目标每帧最多走 0.009153 rad（= 速度 × 5 ms），200 Hz 发帧——按得再快也不会变成一条阶跃指令
```

### 为什么最后要减速

斜坡走到目标**之后手指会往回弹一下**，张开时最明显。原因是 MIT 帧的速度项：`dq` 是
**目标**速度、不是实测值，所以把它从满速一下子降到 `0` 的那一帧，会把阻尼项反过来变成
一个 `kd × v` 的力矩阶跃。本机 `kd = 2.0`、满速 `1.39 rad/s`，那是约 `2.8 Nm`；要在
`kp = 5.0` 下吸收它，需要 `2.8 / kp = 0.56 rad` 的位置误差，也就是 40% 的行程——
位置环找不到这么多误差，机构就回弹来重建它。

所以 05 在到位前先减速：剩余距离短的时候，命令速度取 `√(2·a·remaining)`，减速度
`a = 满速 / 0.15 s`（`RAMP_DOWN_S`）。这个速度永远不会**超过**速率上限，所以上限仍然
是硬边界；它只是让最后几帧慢下来，停下前一帧不到满速的 7%——反向阻尼约 `0.17 Nm`，
而不是 `2.8 Nm`。整段动作最多比按速率上限走多花 `RAMP_DOWN_S`。

SDK 自己的 `_move_at_speed_rad` **不**做这件事——它把 `dq` 顶在满速，停下那一帧直接
置 `0`——所以用 SDK 直接写脚本驱动时，同样的回弹照样出现。

### 真机「能读不能控」了怎么办

```bash
python3 examples/05_dual_control.py --status                  # 只读，不发运动指令
python3 examples/05_dual_control.py --status --clear-fault    # 清掉锁死的故障
```

`--status` 不开窗口、不使能电机、**一帧运动指令都不发**——它只读错误码并翻译它，所以
夹着工件、或手指在别人手里的时候都可以安全地跑。读 DM 寄存器确实会在总线上发读请求，
这和「一帧都不发」不是一回事：它不发的是**运动**指令。

没上电、没使能的电机不主动发状态帧，所以这条路上根本读不到位置。这会被报成「判不了」
并以**退出码 0** 结束，而不是故障：它跳过位置行和错误码行，而不是把 SDK 的初值 `0.0`
当成实测值打出来，寄存器照读。故障只能从状态帧里判，所以需要那个判断就别加
`--status`——那会先使能电机，而使能后的电机会自己持续发帧。

只有 `--clear-fault` 会发帧，而且全是零力矩帧；但 SDK 的清除序列是
disable → clear → enable，中间那一瞬间电机是失力的，手指可能因自重轻微滑动。先托住。

故障是锁死的：不重新上电，它不会自己消失。

### 两种故障长得一模一样，原因不一样

| 码 | 含义 | 什么会触发它 |
| --- | --- | --- |
| 0x9 / 0xA | 欠压 / 过流 | 阶跃指令：默认 kp 下约 10 Nm 电机一帧要 ~185 Nm，本机 5.0 时约 9 Nm |
| **0xD** | **通信丢失**（SDK 自己的 `describe_error` 写作 `通讯丢失 (CAN 超时)`） | 使能态的电机静默约 0.9 s——包括「开着窗口只是看」 |

0xD 是电机的 CAN 看门狗，时长是实测的、不是配置的：**使能态的电机静默约 0.9 s 就锁**。
**空转本身就是故障原因。** 所以本样例在空闲期间按 200 Hz 持续发保持帧（目标 = 实测
位置、前馈为零、不命令任何运动）——见 `IdleKeeper`。更早的版本什么都不发，于是
`enable()` 之后那段安静期——它那 50 ms 的保持流结束、窗口起来、操作员看几秒——就超过
了看门狗并把电机锁死。**那才是「仿真能读真机、但不能控」的主因，不是斜坡。**

别拿 `TIMEOUT` 寄存器（RID 9）推这个时长：它一次读到 8000 ms、另一次读到 0（没有看门
狗），两个都和实测的 0.9 s 对不上，SDK 自己把这条标成「待查」。`--status` 会把寄存器
的实时值打出来存档，并在旁边说明。它打出来的就是下面几行——**照源码抄的，这条路径本机
没跑过**（没有 CAN 硬件），里面的寄存器**数值**只是格式示例，不是实测：

```text
[2] 读寄存器（只发读请求）
   TIMEOUT=0 · CTRL_MODE=1 · UV_Value=15 · OC_Value=0.8 · OT_Value=100
   通信超时保护（TIMEOUT, RID 9）= 0（这个寄存器当前不生效）
   别拿这个寄存器当依据：实测**使能态**的电机静默约 0.9 s 就锁 0xD 通信丢失故障，与寄存器读数对不上（这台机器读到过 8000，也读到过 0），SDK 自己把这条标成「待查」。
      所以 04/05 空闲时照 200 Hz 持续发帧，不赌这个数字；只读不喂帧（或跑了别的只读脚本）同样会把它看哑。
```

同一条总线上有**第二个主站**时症状更乱：两路流互相打架，谁也别想赢。跑真机样例之前，
先确认同一个 CAN 口上没有别的东西（比如 `litegrip_console --backend real`）在跑：

```bash
pgrep -af python3 | grep -i litegrip        # 谁占着 CAN
ip -details -statistics link show can0      # 总线忙？你什么都没跑而计数一直涨，就是别人在说话
```

`ip link set can0 down` / `up` **不会**把它踢掉——它的 socket 还在，接口回来它接着说话。
那个进程必须退出。

本样例自己驱动 CAN 循环，用 SDK 公开的 `send_mit_frame()` 和 `poll()`，而不是
`move_to()` / `goto_rad()`。后者内部跑 `control_mit_stream()`，在自己的循环里睡，从不
让出——窗口会卡死、按键也读不到。公开的帧级接口就是为这种情况留的。

## 上真机之前

三个真机样例都会打印安全横幅，都应当把夹爪拿在手里或夹在台架上跑，**行程内清空**，电源
开关放在手边。05 的第一次先跑 `--dry-run`。

05 第一次接真机跑起来看着像什么都没发生，那是对的：电机已使能，窗口显示的就是夹爪现在
的位置，你不按方向键它就一直在那儿。全程手指别进行程——运动是从按键开始的，不是从确认
开始的。

**只有 03 要保证手在该在的地方。** 录制意味着电机的力被关掉、你的手就放在手指上，所以
夹不到你——那里的风险是你把手指推到了它去不了的地方，或者录制在你扶稳之前就开始了。
回放正好相反：电机在闭环控制下，按标定里的 `kp`、`kd` 跟着轨迹走。而且录完**不会**直接
进入回放：你不按 Enter / 空格它不动，那就是把手拿出行程的时机——所以手指还在行程里时
别按。回放全程手别进行程，并记住手指会带着力停在轨迹终点，直到你退出或样例被停掉。
**别**在一个没预料到夹爪会动的人面前跑回放：你按的那一下**就是**回放，窗口和真机会同时
动起来。

任何东西动起来之前先确认 CAN 口：

```bash
ip -details link show can0
```

### 这次用的是哪份标定

每一条碰真机的路径都从解析标定开始。`--calib <路径>` 用这台夹爪自己的那份：

```bash
python3 examples/05_dual_control.py --calib ~/.litegrip/litegrip_calibration.json
python3 examples/05_dual_control.py            # 不给 --calib：用 SDK 的出厂标定
```

不给 `--calib` 时用的是 SDK 包里那份标定（`factory_calibration.json`，与 `litegrip`
包的 `__init__.py` 同级），启动时会说明。路径从包目录解析，换电脑也跟着检出走。
**那份文件存的是出厂台架夹具的实测参数，不是你这台夹爪的**：它的行程端点可能和眼前这
台对不上。除了第一次看看，都请给 `--calib`。`--dry-run` 解析的是同一份文件，因为就算
不发 CAN 报文，目标角度和毫米刻度也来自它。

只有当出厂文件也读不出来时，才会列出 `~/.litegrip` 下的候选，带 mtime 和关键值
（闭合/张开角、`rad_to_mm`、`kp`、`mst_id`），你按编号选或直接敲路径。上位机给仿真
后端写的 `*.sim.json` 和 `*.bak` 备份永远不会被列出，显式点名 `*.sim.json` 也会被拒
——它的刻度属于仿真夹爪。没有终端可问（管道、脚本、CI）或没有可选项时，运行以退出码 1
停下，并说明怎么拿到标定、怎么传进来。

那份文件来自在上位机（`litegrip-studio` / `litegrip-console`，或 SDK 自带的
`tools/gui/litegrip_gui.py`）里对**这台**夹爪标定后保存。这一点很重要，因为 SDK 的
`load_calibration` 在给定路径读不出来时会**静默**装载自带的出厂标定，并且照样返回
`True`——路径打错一个字母，电机就会按另一台机器的角度去转。所以例程自己读文件、逐字段
确认它真的生效，并拒绝 `can_id` / `mst_id` 指向别的电机的文件。它们还会检查角度自洽：
SDK 的出厂默认就带着一个和它自己 `goto()` 约定矛盾的开角，没标定过的单元会被拦下并
说明原因，而不是拿没有意义的角度去驱动。

### 未经验证

写这些例程的机器上没有 CAN 硬件。03、04、05 里所有与夹爪通信的部分——`connect()`、
`enable()`、录制与回放线程、发帧、`--status` 的寄存器读、`--clear-fault`——都是照着
SDK 源码和 PyBullet 仓库的实测数据写的，**没有**在本机对真机跑过。本文档里的
`--dry-run`、`--play` 和仿真路径跑过，引用的是那些运行的真实输出。硬件路径请先在台架上
确认再信。

## 共用的部分

[`_common.py`](_common.py) 被五个样例共用，它自己不是样例。里面放着参数解析
（`add_common_args()`、`add_hardware_args()`）、SDK 发现（`import_litegrip()`、
`sdk_dir()`、`check_sdk_api()`）、标定解析（`choose_calibration_file()`、
`factory_calibration_path()`、候选列表、「文件是否真的生效」的检查）、连接使能序列
（`open_real_gripper()`）、`make_sim()`、`fresh_state()`、单位换算和状态行。所以每个
样例都是先 `from _common import ...`，**再** import `litegrip_mujoco`。

`fresh_state(gripper, timeout_s=...)` 是读真机位置的唯一途径：`poll()` 只在这次调用
真的解出我们这台电机的状态帧时才返回 `True`，紧跟其后的快照才是实测值。**别**直接读
`get_state(wait=False)` 当作位置——没有帧托底时它返回的是 SDK 的初值 `0.0`，看着像
读数，其实不是。这里刻意没有第二道新鲜度门槛：这个 SDK 没有公开「这份快照是否有数据
托底」的标记，`poll()` 就是全部信号。

`make_sim(headless)` 是本仓对 `pkg.connect(GUI)` 的替代：按自带的 MJCF
（`litegrip.xml`，给 `--scene` 时用 `scene.xml`）建一个 `MujocoGripper`，无头时关渲染。

## 从 PyBullet 那套例程过来

两个仓库讲同样的五个故事，但用的是不同的库——`litegrip-pybullet` 驱动 `pybullet`，本仓
通过 `MujocoGripper` 驱动 MuJoCo，而 `MujocoGripper` 镜像的是 `litegrip.LiteGrip` 这个
SDK 类，不是一套仿真专用 API。场景、分节编号、终端输出都对得上，名字大多对不上：

| PyBullet | MuJoCo | 说明 |
| --- | --- | --- |
| `GripperSim(...)` | `make_sim(headless)` → `MujocoGripper` | 仍然由 `connect()` / `disconnect()` 括起来 |
| `sim.step()` | `sim.pump()` | 推事件、走时钟；窗口被关时返回 `False` |
| `sim.reset_fraction(f)` | `sim.set_frac_open(f)` | 运动学直接摆位，**并且同时设控制器目标**，所以手指是被顶住而不是掉下去 |
| `sim.fraction()` | `sim.frac_open()` | 归一化开度 |
| `sim.aperture_mm()` | `sim.gap_mm()` | 钳口间隙，不是开口行程 |
| `sim.run_for(s)` / `sim.settle()` | `sim.settle(...)` | `settle()` 返回 `(elapsed_s, reached)` |
| `sim.grasp_center()`、`contacts()`、`add_box()` | 同名 | `add_box()` 复用 MJCF 里四个预留槽位之一 |
| `SliderDrive` | `KeyboardDrive` | 斜坡与 `RAMP_DOWN_S` 减速完全一致 |
| 窗口里的三个滑条 | 方向键 + 状态文字图例 | MuJoCo 查看器没有控件 API |
| `mouse_events()`、`clicked()` | 同名 | 保留为哑元：永远返回 `[]` 和 `False`，因为 `launch_passive` 不给鼠标事件（03 因此改成 Enter / 空格） |
| `sim_motor_params()` | —— | 没有加：`--status` 只在真机路径上可达，那里唯一会调的就是 SDK 自己的 `read_param()` |
| `--no-mirror-first` | —— | 去掉：它属于旧的双手爪设计，在这里没有含义 |

两个行为变化，凭记忆跑旧文件的人要知道：标定相关的拒绝现在退出码是 **1**
（`SystemExit(message)`），不是 2——2 留给 argparse 自己的用法错误；05 的 `--headless`
在没给 `--dry-run` 时会被拒，因为键盘就是输入设备。

## 说明

### `grasp()` 到底做了什么

`grasp(force_n=N)` 设的是**前馈力矩**，不是闭环的夹持力设定值。位置环还接着，工件顶
回来，目标位与实测位差出一点角度，`kp × Δθ` 就加在前馈上。2026-09-30 用
`python3 examples/02_move_sim.py --headless --scene --force 10` 实测：

| 请求 | `get_force()` 报 | 超出 |
| --- | --- | --- |
| 10 N | 15.51 N | +5.5 N |
| 0 N | 6.2 N | +6.2 N |

指面侧的接触力同样读到 15.51 N（每侧 4 个接触点），所以模型和报出来的数字是一致的；
是那个**请求值**只是个基准，不是设定值。真机上是否同样超调**未经验证**——本机没有 CAN
硬件。

### 夹持中心在哪

`sim.grasp_center()` 在纯夹爪模型里返回 `[0.0, 0.0, 0.096735]` m，即两个指面的中点，
也是工件该放的位置。这是按自带的 `litegrip.xml` 实测的；换模型这个数就变，所以请读它，
别写死。

**别**从 `link_aabb()` / `pad_aabbs()` 读钳口开度：那是**碰撞**包围盒，刻意做得粗
（见开发者指南里的「Why collision uses boxes, not meshes」），并不是间隙。开度用
`gap_mm()`，谁碰到了谁用 `contacts()`。

### 03 走自己的连接封装

`_common.open_real_gripper()` 自己会 import SDK，但 03 在 `main()` 里先 import 一次，
好让 API 检查发生在别的任何事情之前，然后把那个模块传给它自己的 `open_gripper()`。
标定、连接、校验、使能这几步是同一套，只是模块的来源不同。

### 开窗口的运行以 `Segmentation fault` 结束

如果一个开了查看器的运行在打印完收尾那行**之后**以 `Segmentation fault (core dumped)`
结束，那么这次运行本身是成功的——那是上游在进程退出时的 GL 拆卸崩溃，不是仿真失败。
`--headless` / `--no-render` 不受影响。详见开发者指南。
